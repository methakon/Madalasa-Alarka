## What already existed, and what this task adds

The read path (`backend/src/free_location_reads.h`) already clamps the window server-side to
`interval '6 hours'` and returns `history_window_hours = 6`. What was missing was an
automated guard proving the two properties the acceptance names — that the free endpoint
**cannot exceed** six hours, and that the **storage gate remains distinct**. This task adds
that guard rather than re-implementing the endpoint.

## Acceptance

> "Free endpoint cannot exceed 6h while storage gate remains distinct"

- **Cannot exceed 6 h:** the window is a fixed SQL predicate anchored to
  `statement_timestamp()`, the response advertises `history_window_hours = 6`, the page size
  is a server constant (`200` history, `1` latest), and the handler refuses *all* query
  parameters so no caller-supplied range exists to widen. Both free routes (`/location/latest`
  and `/location/history`) are asserted to use the same clamped reader.
- **Storage gate distinct:** the read path is asserted to contain no `retention`,
  `retain_for`, `purge`, `delete from` or `ttl` behaviour, so six hours can never become a
  six-hour deletion schedule; and `retention_policy.h` is separately asserted to still
  default to `Undecided` with `scheduling_enabled{false}` and no positive approved period.
  This is the L15-001 component: no category inherits the visibility window.

## Negative cases covered

- Any query parameter on a free read is rejected outright, so widening attempts fail closed.
- Presence of retention/purge/deletion logic inside the read path fails the contract.
- Absence of the retention component's fail-closed default fails the contract, i.e. the
  storage gate cannot silently become permissive.
