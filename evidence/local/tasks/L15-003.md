## Acceptance

> "Delete request not mistaken for immediate completion"

1. **Explicit Pending Contract:** When a valid child erasure request is accepted by `POST /v1/children/{childId}/erasure-requests`, the response status is strictly `202 Accepted` (never `200 OK`).
2. **Boolean `completed: false`:** The response body explicitly specifies `completed: false` and carries notice: `"Request recorded; primary deletion and external/backup verification are separate."`.
3. **Payload Strictness:** Requires explicit `confirm_child_erasure: true` boolean and an `Idempotency-Key` UUID header. Omitting the flag, setting it to `false`, adding extraneous fields, or sending a body > 1024 bytes fails closed with `422 VALIDATION_FAILED` or `400 INVALID_REQUEST`.
4. **Child-Scope RLS:** Authorization checks require a valid parent session with `MANAGE_CHILD_GRANTS` on that exact child; cross-family or unauthenticated attempts return `401` or `404/403`.
5. **Durable Tombstone & Restore Resistance:** Verified in PostgreSQL integration (`test_privacy_admin.py`): primary erasure sets state `PRIMARY_ERASED`, immediately suspends device credentials, removes active rows from child tables, and inserts a durable tombstone that prevents erased child resurrection during restore runs.
