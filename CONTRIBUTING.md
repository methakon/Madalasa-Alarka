# Contributing to Madalasa–Alarka

The project is in **design/M1 contract and synthetic database test stage**. It is **not** a deployed child monitoring system. Before proposing work, read [SRS](docs/phases/M1-secure-platform-foundation/01-requirements-and-architecture/SRS.md), [Blockers](docs/phases/M0-foundation-and-approvals/01-project-governance/BLOCKERS_AND_OWNER_DECISIONS.md), [Developer Onboarding](docs/phases/M1-secure-platform-foundation/02-development-process/DEVELOPER_ONBOARDING_AND_CODING_STANDARDS.md), [Security](SECURITY.md), and [License decision](docs/phases/M0-foundation-and-approvals/03-legal-and-privacy/LICENSING_DECISION_AND_IP_REGISTER.md).

## Contributions
1. Open a scoped issue (feature/bug), referencing requirement ID, acceptance tests and a privacy/security impact statement. Do not post real children's information, GPS, screenshots or credentials.
2. **Use existing permanent workstream branches** (`api`, `parent`, `child`, `admin-web`) based on `main`. The next hop for every code PR is `dev`, followed by tested, reviewed `dev` → `main`. An additional `temp/<task>` branch requires explicit owner instruction and is deleted only after verified integration to `main`. Read the [binding branch policy](docs/phases/M1-secure-platform-foundation/02-development-process/BRANCHING_VERSIONING_AND_RELEASE_PROCESS.md).
3. **Before beginning/resuming work or submitting a code PR, synchronise both `main` and `dev`** using `bash docs/tools/sync_work_branch.sh <current-branch>` from a clean worktree. Document the remote SHAs and resolve conflicts without overwriting other workers' work. The `main` documentation preflight fetches `dev` for inspection but never merges unverified development work into `main`. Then run existing M1 Python structural lint and PostgreSQL synthetic RLS tests following [Build and Run](docs/phases/M1-secure-platform-foundation/02-development-process/BUILD_AND_RUN.md). New Android/C++ tests become mandatory **when source projects exist**.
4. Keep canonical SRS, ADR, OpenAPI, planning and documentation edits on `main` only, coordinated by a documentation maintainer; workers propose the necessary doc deltas rather than editing docs on code branches. Keep SQL migrations and executable tests on their workstream branch; verify contract synchronization before each promotion. Never weaken child-scoped grants or OS privacy controls.
5. Open a code PR to `dev` using the template, disclose dependencies/licenses, tests performed/not run, target-SDK impact, data collected and new permissions. Validate the cumulative `dev` tree before promotion, then run final testing on the actual merged `main` commit.
6. Obtain designated backend, mobile and security/privacy review as applicable; no self-approval of high-risk changes.

Do not add covert capture, Android permission bypasses, raw children's media/position to CI, or undocumented child-monitoring features. Report vulnerabilities **privately** via [SECURITY.md](SECURITY.md), not issues.
